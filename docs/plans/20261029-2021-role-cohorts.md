# Role cohorts - implementation plan

**Spec:** docs/specs/2026-10-29-role-cohorts-design.md

**Goal:** Circles, the deck dialog, history, trends, the home page and `/api` use one role definition (9 cohorts,
an estimator pool for the overall score); the DEV/QA split remains only in legacy `/api` fields; the results circle uses
ECharts in a lazy chunk.

**Architecture:** The original Tasks 1-12 are complete and remain as implementation history. The Tasks 13-15 revision adds
automatic circles on top of the current implementation: first a separate vote grouping function, then its integration
into the room and removal of the setting, followed by documentation updates and an integration check. Statistics
functions for raw built-in cohorts and the API retain their current contract. Custom keys use the `custom:` namespace;
the label is the name without the prefix. Circles use the existing lazy-loaded ECharts. Tasks 13-15 are sequential
because they share models and tests; parallel mutations are n/a: each task consumes the previous one. The main checkout
and current branch are retained; PR64 has an existing separate worktree, and its header and modal changes must be
preserved during further integration.

**Stack:** React 19, TypeScript 7, Vite 8, ECharts (`echarts/core`, `useEChart`), Zustand, i18next, Vitest +
happy-dom + Testing Library, Netlify Functions, `agent-browser` for manual verification.

**Execution:** subagents - sequential tasks; the controller checks each result in the shared checkout

## Global constraints

### Decisions

1. Built-in role cohorts: `DEV, BE, FE, SRE, QA, GQA, AQA, PO, SM` in that order. Each custom role gets its own
   circle; custom roles follow built-in ones in the order of the first voting participant in the current room list.
   A player with no role or absent from visible players is `DEV`.
2. Circles are determined automatically from actual votes after reveal. Only a role with at least one vote is shown,
   regardless of the number of participants with that role. Three roles with votes produce three circles; eight roles
   present but only two having votes produce two circles. Circles without votes are absent.
3. The “Show results” section has been removed. Any valid saved `room_state.result_cohorts` value is ignored for
   display; saving a deck no longer changes the field. The schema and old data remain compatible. Automatic display
   was chosen over chips at the owner's direct request.
4. Automatic custom circles apply only to current-round results. Built-in cohorts for history, trends, the home page
   and `/api`, the estimator definition and API compatibility remain as decided below. A custom role's identity is its
   full saved shield value with the `custom:` prefix; identical values are grouped, distinct values are not merged,
   even when the label matches a built-in role name.
5. The overall round score (average and alignment) uses one pool of estimator votes: `DEV, BE, FE, SRE, QA, GQA, AQA`
   roles, excluding PO/SM and custom roles. If only non-estimators voted in the round, the pool is all votes. The score
   is an integer from 0-100 from cards excluding `?`/`☕`, or `null` with fewer than two such votes. The history list,
   home page, trend cards and `/api` `average`/`voters` use this definition. Take the estimator pool over the average
   of roles: history and `/api` already calculate it this way, so their numbers do not change. The cost is a shift in
   home page and trend card numbers (the home page previously averaged DEV and QA; cards averaged roles including
   PO/SM). Rejected: averaging role scores would change historical numbers in history and `/api`.
6. Trend cards retain their formulas; only the input round score changes (decision 5). “Current score” is the last
   non-null score in the visible period. “Average score” is the rounded average of non-null scores. “Trend” compares
   the second half of non-null scores with the first when there are ≥ 4 scores; a change over ±1 % is up or down,
   otherwise stable. The home page uses the rounded average of non-null overall round scores from numeric decks
   (`scrum, fibonacci, hours, goal_clarity` and rounds without a preset), the same set of rounds as trends. Take the
   shared filter over the current “all rounds”: poll rounds no longer enter the room score.
7. `/api` is extended without breaking compatibility. Each round gets `alignments` and `roleVotes`. `alignments` is
   sparse: a key exists only for a role with at least one vote, and its value is an integer 0-100 or `null`.
   `roleVotes` contains all votes with a cohort, each with a `role` field. `average`, `voters`, `devAlignment`,
   `qaAlignment` and `votes[{name,vote,cohort}]` remain byte-for-byte as before, as does the set of rounds in the
   response. Take new fields alongside existing ones over replacement: agilecharts works unchanged; the cost is a copy
   of the old DEV/QA split in the function as a legacy contract. Rejected: replacing fields breaks the Estimation
   Trends tab in agilecharts.
8. Trend chart: one line per role with a score in the visible period; each can be hidden in the legend. “Details” on
   a line point shows only that role's votes. Take role lines over DEV/QA: for built-in roles, as in circles.
9. History list: if round votes with a cohort belong to two or more roles, show one row per role (colored role badge
   + card counts) in decision 1 order. Custom role votes go in a final row without a badge. A round with one role or
   only custom roles shows one row of counts for all votes, as before. Take role rows over DEV/QA rows; take a separate
   custom row over discarding them: the number of votes in rows equals the number of round votes.
10. Consensus celebration and sound stay as before: they trigger when a visible circle has ≥ 2 votes and one estimate.
    Any role's circle qualifies, including PO/SM and custom; all votes belong to their own circles. Read “more than one
    teammate” as ≥ 2 votes in a circle, rather than ≥ 2 players with the role in the room. Take votes over members:
    one voter out of three POs has nobody to agree with.
11. ECharts (pie) draws the results circle in a lazy chunk, like the trends modal. All circles are alike: width 240 px;
    on a screen too narrow for 240 px, all shrink equally. One vote gives a solid circle with the card label; multiple
    votes give sectors with card labels and the same palette. The `<ROLE>: <average>` label renders
    outside the chart and is visible immediately. While the chunk loads or if it fails, an empty space of the same
    size replaces the circle, without an on-screen error. Take lazy ECharts over eager loading: the entry-chunk budget
    is `icons:audit-build`; the cost is that the circle appears after the chunk loads (instantly from the PWA cache).
    Rejected: retaining SVG, due to the historical `app/components/AGENTS.md` rule «при дотику переписуй на ECharts»
    (“rewrite to ECharts when touching it”).
12. Role colors use one map everywhere: trend lines, history badges and round snapshot badges. Existing colors stay
    unchanged; new ones are GQA `#ff7043`, AQA `#fdd835`, both distinct from QA `#ffa726`.
13. After the transition the app has no DEV/QA split: functions and constants that calculate or label it disappear,
    and documentation describes only role cohorts. The sole deliberate remainder is the legacy `/api` fields
    (decision 7), marked in code and documentation as an agilecharts contract.

### Out of scope

1. Changes in agilecharts: migration to `alignments`/`roleVotes` is separate work in that repository.
2. The role at the time of a historical vote: this requires a field in `round_history.votes`.
3. Database migrations and changes to the check constraint.
4. Custom trend lines, custom `/api` keys and changes to the overall score definition through the new circles.
5. Clients with an old PWA bundle before updating: they display QA in one circle and the old score. The data and
   schema remain the same, so there is no breakage; updates arrive through the usual `useAppUpdate` mechanism.

### Security Model

Trusted inputs: the owner's decisions in this conversation. Untrusted inputs: Supabase data (`round_history.votes`,
names, shields) and `/api` requests. Player names in `roleVotes` do not exceed what `votes` already returns and what
anyone in the room can see. The endpoint remains protected by `Authorization: Bearer <STORYPOKER_API_TOKEN>`. The change
adds no network calls, secrets, RLS or schema changes, and the client receives no data it did not already have. Custom
names are displayed as ordinary text without HTML; long names wrap, and custom role keys are not mixed with built-in keys.

## Review focus

1. Compatibility of the already implemented history, trends, home page and legacy API: custom circles do not change
   `cohortForShields`, `voteCohortFor`, `estimatorVotes` or the statistical identity of roles.
2. Custom keys named DEV/QA, identical names, the first role among legacy shields, long names and numeric and special
   cards; no HTML from role data.
3. Repeated reveal and width changes leave no stale charts; labels do not overlap adjacent circles.
4. All renderers of current and latest results and snapshot replay must preserve a stable key separately from the label.
   Previous log entries and Tasks 1-12 describe the historical contract before the revision.
5. A separate pre-squash gate is required before squash. The last run on the old tree has Visual differences; they must
   not be concealed by updating the baseline or weakening the threshold.
